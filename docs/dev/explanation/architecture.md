# Architecture

## Mission

A secure, self-contained ARK: Survival Ascended server image, operated
through Docker Compose (or rootless Podman) today, with room for other
orchestrators (Kubernetes) later.

## Three-layer architecture

```
┌─────────────────────────────────┐  ┌──────────────────────────────┐
│  CLI: app/ark-cli (Go binary)   │  │  Web UI: app/ark-web (Go)    │
│  command routing, flag parsing, │  │  HTTP routes, templates      │
│  handler dispatch               │  │                              │
└───────────────┬─────────────────┘  └──────────────┬───────────────┘
                │  domain services via AppDeps      │  domain services via server.Deps
┌───────────────▼───────────────────────────────────▼───────────────┐
│  Domain: app/pkg/ark (Go packages)                                │
│  backup, health, lifecycle, schedule, update services             │
└───────────────┬───────────────────────────────────────────────────┘
                │  ContainerEngine / ComposeService interfaces
┌───────────────▼─────────────────┐
│  Backend: app/pkg/ark/sdkbackend│  Docker Engine SDK + embedded
│                                 │  Compose library
└───────────────┬─────────────────┘
                │  Docker / Podman API
┌───────────────▼─────────────────┐
│  Container: runtime scripts     │  server process, RCON control,
│  container/scripts/runtime/     │  default INI, log tailing,
│  (Python + Bash)                │  saves, backup/restore
└─────────────────────────────────┘
```

The host side never manages the ARK server process directly. It orchestrates
containers through domain services that call the backend interfaces. All
server-state operations (save, graceful stop, backup) go through RCON or
container-internal scripts.

### Container script boundary

The runtime scripts in `container/scripts/runtime/` are the container's API.
The CLI, ark-web and any other host process call them through
`ComposeService.Exec` or `RunOneOff`, and read their output and exit code.
They never read, write or delete files inside a container themselves, and
never run inline shell (`sh -c "cat …"`, `mv`, `rm`) against container paths.
File formats such as the INI files are parsed only by container scripts, so
the image can change its layout without breaking the host side.

A host feature that needs something from inside the container adds or extends
a runtime script, with tests in `tests/container/`, and calls that. Rule and
current exceptions:
[conventions.md](../reference/conventions.md#container-access).

The SDK backend implements both `ContainerEngine` and `ComposeService` and
must pass the conformance tests in `app/pkg/ark/conformance/`. See
[backends.md](backends.md).

## Container startup flow

```
container-entrypoint.sh
  └─ if root: exec setpriv to ark-user (replaces the process, so the shutdown
     manager is not killed by a lingering parent)
  └─ exec container-entrypoint.py
       └─ command override args present: os.execvp them (maintenance use;
          sets ARK_MAINTENANCE_MODE=restore when the command is ark-restore.py)
       └─ otherwise: run_default_startup
            └─ warn on low RAM headroom or low host kernel params
            └─ check data dirs: Saved/ and Saved/clusters must exist and be
               writable; refuse to start if no volume is mounted at Saved/;
               warn if none at Saved/clusters
            └─ no GameUserSettings.ini on the volume: install the image's default
               (/home/ark-user/config-defaults/, generated by ARK at image build)
            └─ apply RCON/password settings from env to GameUserSettings.ini
               (skipped with a warning if SERVER_ADMIN_PASSWORD is unset)
            └─ exec ark-server-start.py
                 └─ start ARK server via GE-Proton
                 └─ tail ShooterGame.log → container log output
                 └─ on SIGTERM/SIGINT: run ark-server-stop.py
                      └─ SHUTDOWN_WARNING_MINUTES>0 and players online: countdown warnings
                         (ServerChat + Broadcast at 10/5/1 min, 30 s; reason from ark-stop-reason.py)
                      └─ saveworld (retried until confirmed in the log) → DoExit
                      └─ wait for exit; else SIGTERM, then SIGKILL the process group
                 └─ on server exit: report an OOM kill if the cgroup oom_kill counter rose
```

Any failed check before `exec ark-server-start.py` exits 1. The default INI
install and the RCON settings run on every start, so a new volume gets ARK's
defaults and the INI always matches the compose environment. See
[design-decisions.md](design-decisions.md#why-gameusersettingsini-is-baked-into-the-image).

## RCON as the control plane

All in-game operations (save world, graceful shutdown, admin commands) use
RCON on `RCON_PORT`. Container scripts speak it in-process through
`rcon_client.py`, a standard-library client. Everything else (`ark-cli save
instance`, CI, benchmarks) runs `ark-rcon.py <command>` inside the container.
Both read the password from `SERVER_ADMIN_PASSWORD`, so it never appears on a
command line (visible to any host user via `ps`).

Dropped alternatives:
- external `rcon-cli` binary: password on argv, and its output text had to be
  parsed;
- `conqp/rcon` library: archived, with open crashes on unexpected packet types
  (the in-house client ignores them).

The host side therefore never needs to understand ARK game state: it issues
instructions to the container and reads results from container logs or exit
codes. Rationale:
[design-decisions.md](design-decisions.md#why-rcon-is-the-primary-control-plane).

## Compose YAML AST editing

The CLI edits `docker-compose.yaml` with `goccy/go-yaml` at the AST level,
preserving user comments and formatting instead of regenerating the file from
a template. All compose reads go through `ComposeService.LoadProject` and all
writes through `ComposeService.SaveProject`; no command handler loads or saves
compose files directly. Direct file I/O bypasses project name derivation
(Compose v5 then fails with "project name must not be empty") and loses the
AST preservation.

## Seam dependency injection (Go CLI)

`AppDeps` groups side-effecting functions and domain services into injectable
fields: `Engine` (`ark.ContainerEngine`), `ComposeService`
(`ark.ComposeService`), and the domain services `HealthChecker`
(`health.InstanceHealthChecker`), `Lifecycle`, `BackupService`,
`UpdateService`, `ScheduleService` from `app/pkg/ark/`. Tests swap individual
functions or services without patching package globals, so every command
handler is testable without a container runtime.

Struct layout: `app/ark-cli/internal/core/deps.go`. Testing patterns:
[test-architecture.md](../reference/test-architecture.md).

## Primary design goals

- Docker Compose usage stays approachable for inexperienced admins.
- Secure defaults: the server runs as `ark-user`, not root; RCON is published
  on 127.0.0.1 only.
- Manage the server through container-internal scripts invoked via the
  container runtime.
- Use RCON and server logs to verify save, shutdown and crash handling.
- Compose-friendly today, Kubernetes-compatible later.

Rationale for specific choices: [design-decisions.md](design-decisions.md).
