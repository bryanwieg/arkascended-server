# Architecture

## Mission

Deliver a secure, self-contained Dockerized ARK: Survival Ascended server
that is easy for inexperienced admins to operate via Compose today, while
leaving room for more advanced orchestration (Kubernetes, etc.) in the future.

## Three-layer architecture

```
┌─────────────────────────────────┐
│  CLI: app/ark-cli (Go binary)   │  command routing, flag parsing,
│                                 │  handler dispatch
└───────────────┬─────────────────┘
                │  calls domain services via AppDeps
┌───────────────▼─────────────────┐
│  Domain: app/pkg/ark            │  backup, health, lifecycle,
│  (Go packages)                  │  schedule, update services
└───────────────┬─────────────────┘
                │  ContainerEngine / ComposeService interfaces
┌───────────────▼─────────────────┐
│  Backends: sdkbackend           │  Go SDK calls
└───────────────┬─────────────────┘
                │  Compose SDK / Engine SDK API calls
┌───────────────▼─────────────────┐
│  Container: runtime scripts     │  server process, RCON control,
│  (Python + Bash)                │  default INI, log tailing, saves
└─────────────────────────────────┘
```

The host CLI never manages the ARK server process directly. It orchestrates
containers through domain services that call backend interfaces. All
server-state operations (save, graceful stop, backup) go through RCON or
container-internal scripts.

The SDK backend (`app/pkg/ark/sdkbackend/`) implements both `ContainerEngine`
and `ComposeService` interfaces and must pass the shared conformance tests in
`app/pkg/ark/conformance/`.

## Container startup flow

```
container-entrypoint.sh
  └─ drops to ark-user if running as root
  └─ exec container-entrypoint.py
       └─ if command override args present: os.execvp (allows maintenance use)
        └─ otherwise: run_default_startup
             └─ warn on low host RAM or kernel params; check volume mounts
                (refuse to start if no volume is mounted at Saved/; warn if none at Saved/clusters)
            └─ if the volume has no GameUserSettings.ini: install the image's default
               (/home/ark-user/config-defaults/, generated by ARK at image build)
            └─ apply RCON/password settings from env to GameUserSettings.ini
            └─ exec ark-server-start.py
                 └─ start ARK server via GE-Proton/Wine
                 └─ tail ShooterGame.log → Docker log output
                 └─ on SIGTERM/SIGINT: invoke ark-server-stop.py
                       └─ if SHUTDOWN_WARNING_MINUTES>0: broadcast shutdown warning via RCON chat, then wait
                      └─ saveworld (retried on transient failure) → DoExit
                      └─ wait for clean exit; force-kill on timeout
                 └─ on server exit: report an OOM kill if the cgroup oom_kill counter rose
```

First boot needs no special step: any start that finds no
`GameUserSettings.ini` installs the image's default, which ARK wrote during the
image build. The RCON and password settings are re-applied on every start, so
they always match the compose environment. See
[design-decisions.md](design-decisions.md#why-gameusersettingsini-is-baked-into-the-image).

## RCON as the control plane

All in-game operations (save world, graceful shutdown, admin commands) go
through the RCON protocol on `RCON_PORT`. The container-side scripts speak it
in-process through `rcon_client.py`, a small standard-library client; anything
outside the scripts (`ark-cli save world`, CI, benchmarks) runs `ark-rcon.py
<command>` inside the container. Both read the password from
`SERVER_ADMIN_PASSWORD`, so it never appears on a command line, which any host
user can read with `ps`. The external `rcon-cli` binary was dropped for that
reason, and because its output text had to be parsed. The archived `conqp/rcon`
library has open crashes on unexpected packet types, which the client ignores.

This means the host CLI never needs to understand ARK game state — it issues
instructions to the container and reads results from Docker logs or exit codes.

## Compose YAML AST editing

The CLI edits `docker-compose.yaml` using `goccy/go-yaml` for surgical
AST-level modifications. This preserves user comments and formatting instead
of regenerating the file from a template on every change. All compose reads
go through `ComposeService.LoadProject` and all writes go through
`ComposeService.SaveProject`; no command handler may load or save compose
files directly. Direct file I/O bypasses the project name derivation
(causing "project name must not be empty" on Docker Compose v5) and loses
the AST-preservation logic.

## Seam dependency injection (Go CLI)

`AppDeps` groups side-effecting functions and domain services into injectable
fields. Container orchestration goes through `ark.ContainerEngine` and
`ark.ComposeService` interfaces, with domain services (`backup.Service`,
`health.Checker`, `lifecycle.Service`, `schedule.Service`, `update.Service`)
as separate packages in `app/pkg/ark/`. Tests swap individual functions or
service interfaces without patching package globals. This makes every command
handler fully testable without a running Docker daemon.

See `app/ark-cli/internal/core/deps.go` for the struct layout and
`docs/dev/reference/test-architecture.md` for the testing patterns.

## Primary design goals

- Keep Docker Compose usage simple for inexperienced admins.
- Default to secure behavior; container runs as `ark-user`, not root.
- Manage the server through container-internal scripts invoked via Docker.
- Use RCON and server logs to verify safe save/shutdown and crash handling.
- Compose-friendly today, Kubernetes-compatible later.

For the rationale behind specific choices, see
`docs/dev/explanation/design-decisions.md`.
